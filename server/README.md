# Custom game server

The server replaces Firebase Authentication, Firebase level storage and the
separately hosted account manager. Accounts, sessions and levels live in one
SQLite database. No cloud keys or third-party Python packages are needed.

Run from the repository root with Python 3.11 or newer:

    python server/game_server.py

Open http://127.0.0.1:8080 to create an account, then sign in inside the game.
The game defaults to this address. On a physical Android device, localhost is
the phone: use your computer's LAN address and run with --host 0.0.0.0, or use
adb reverse tcp:8080 tcp:8080 for USB development. The Android emulator can use
http://10.0.2.2:8080.

Set assets/config.json's level_server_url, level_api_url and account_manager_url
to the server address; also set settings.network.level_server_url in
assets/client_settings.json before packaging. Existing saved Firebase endpoints
are migrated to the configured server and old login tokens are cleared.
Users need new accounts. Import old levels with the operator command below; passwords and accounts are not imported.

Configuration (CLI flags override environment variables):
- --host / HOST: bind address, default 127.0.0.1.
- --port / PORT: port, default 8080.
- --database / DATABASE_PATH: defaults to server/data/game.sqlite3.
- --public-url / PUBLIC_URL: advertised HTTPS address.

For deployment, put the server behind an HTTPS reverse proxy and keep port 8080
private. The included Docker Compose and Caddy config provide HTTPS when DOMAIN
points to the host and ports 80/443 are reachable. Run:
    DOMAIN=game.example.com docker compose -f server/compose.yaml up -d --build
Set the game's configured URLs to https://game.example.com before building.
This repository does not provision a host, DNS or certificates itself.

Persistence: keep the data directory or Docker volume across updates.
Stop the server before copying the database for a backup (include any -wal and
-shm files), or use SQLite's online backup API. Never publish the database.
SQLite transactions protect account uniqueness and level ownership. Ownership
uses immutable account IDs, so renaming an account retains its levels.

API:
- POST /api/auth/register: email, password (10–256 chars), displayName.
- POST /api/auth/login: email, password.
- POST /api/auth/lookup: Bearer token, or idToken in JSON.
- POST /api/auth/update: Bearer token, currentPassword, displayName/password.
- POST /api/auth/logout: Bearer token.
- GET /levels.json?shallow=true: object mapping level IDs to true.
- GET /levels/<id>.json: full level; GET /levels/<id>/data.json: JSON string.
- PUT /levels/<id>.json: Bearer token, name, data, optional api_version_id.
- DELETE /levels/<id>.json: Bearer token, owner only.
- GET /health and GET /api.json: health and service descriptor.

Login returns idToken, localId, email, displayName, expiresIn. These response
field names preserve the game's parser; tokens are generated by this server,
stored hashed and expire after 30 days. Password changes and username changes
revoke existing sessions. Level owner and timestamps come from the server,
never from untrusted upload fields. Public levels can be read without login.
Writes are limited to 2 MiB per request and 100 levels per account. Account
routes allow 20 requests per minute per peer IP. Behind a proxy this is a shared
limit; add per-client rate limiting at the proxy when hosting many players.
Passwords use salted scrypt. Browser sessions are stored only for the tab.

This version provides accounts and asynchronous level sharing, not realtime
multiplayer or email verification/password recovery. Do not advertise email
ownership as verified. A forgotten password requires an operator-managed
recovery process; there is no insecure public reset endpoint.

Tests:
    python -m unittest discover -s server -p "test_*.py" -v

The server uses Python's standard HTTP implementation with bounded concurrency;
load-test for the expected player count before public rollout.


Optional update hosting: put update-manifest.json and release installers in
server/releases (or --releases / RELEASES_PATH). The server exposes the manifest
at /update-manifest.json and installers at /releases/<filename>. The default
game config uses this manifest URL. Until a manifest is published, update checks
report that it is unavailable. An example manifest:
    {"version":"2.3.1","version_id":27,
     "installer_url":"https://game.example.com/releases/game-setup.exe",
     "notes":"Release notes"}
For Docker, populate the game-releases volume with these operator-published
files. The HTTP API cannot publish or alter executables.


To update all packaged server URLs together:
    python server/configure_game.py https://game.example.com
Then rebuild the game. This preserves unrelated app settings.


Import levels from the old server:

1. Start the custom server and create the account that will own the imports.
2. Preview the import (replace admin with that account's username):
       python server/import_levels.py --owner admin --dry-run
3. Import:
       python server/import_levels.py --owner admin

The default source is the previous timetravel-server-default Firebase database.
Only GET requests are sent to it; the old levels are never changed or deleted.
Use --source https://your-old-database.example for a different source, or:
    python server/import_levels.py --owner admin --file old-export.json

Files can contain either the /levels.json response or a complete Firebase
database export with a levels node. Use --database /path/to/game.sqlite3 to
select the destination. DATABASE_PATH is also supported. The database and
destination account must already exist. With the portable workspace runtime,
replace python with .\.tools\python-server\python.exe.

Existing level IDs are always skipped, never overwritten or reassigned.
IDs, names, raw level text, API versions and upload timestamps are retained;
missing names default to the ID, missing API versions to 1, and missing
timestamps to 0. Invalid entries are reported and skipped. A database error
rolls back the entire batch. The JSON report lists imported, skipped and
failed entries; dry runs list would_import without inserting any data.
Exit codes: 0 = success, 1 = fatal error, 2 = some records were invalid.

Ownership is assigned explicitly. The original author is kept in the
level_imports provenance table; public ownership belongs to the selected
new account. To assign different authors to different existing accounts, use
--owner-map owners.json, for example:
    {"old-author": "new_username", "another-author": "another_username"}
Unmapped authors use --owner. Unknown destination accounts abort the import.
Legacy names never automatically grant ownership to a newly registered user.
This operator import bypasses the normal 100-level upload quota so that a full
archive can be migrated; normal authenticated upload limits still apply.

If the old database requires authentication, set LEGACY_SERVER_TOKEN in the
environment before running the importer. Authenticated downloads require HTTPS,
do not follow redirects, and never print the token. --token-env changes the
environment-variable name. Exports are limited to 128 MiB by default; use
--max-bytes to raise that limit and --timeout to change the 30-second timeout.

Docker (after rebuilding the image):
    docker compose -f server/compose.yaml exec game python server/import_levels.py --owner admin --dry-run
Remove --dry-run to import into the mounted game-data volume.
Difficulty ratings and moderators:

Shared levels start Unrated. A moderator can assign an integer from 1 (easiest)
to 9 (hardest). The game shows this rating in the shared-level list on desktop
and Android. Local and built-in campaign levels have no server rating.

Grant a moderator role to an existing account from the server host:
    python server/moderators.py --grant USERNAME
Revoke it:
    python server/moderators.py --revoke USERNAME
Both commands support --database and DATABASE_PATH. No public endpoint grants
roles. Existing sessions lose rating permission immediately when access is
revoked; account registration and profile updates cannot grant moderator roles.

Reload the account manager after a role change. Moderators see a Level difficulty
panel: refresh levels, choose a level, select 1-9, and set its difficulty.
The API is PUT /levels/<id>/difficulty with a Bearer token and {"difficulty": 5}.
GET /levels.json?metadata=true returns level metadata and difficulty without
downloading all level content. Full level responses also include difficulty;
null means Unrated. Existing shallow-list and data-download formats still work.

Ordinary uploads cannot set difficulty, even when the uploader owns the level.
Changing a level's content clears its rating for moderator review; changing only
its name preserves the rating. Imported levels start Unrated. Ratings and roles
are persisted in SQLite; existing databases get the new tables automatically.
Moderator identity and rating time are recorded with each current rating.
Game lists refresh when reopened. No difficulty changes are trusted from local
level files, upload payloads, or the old server's imported metadata.

For Docker, rebuild the image and run:
    docker compose -f server/compose.yaml exec game python server/moderators.py --grant USERNAME

Local administration dashboard:

Starting python server/game_server.py now also starts the dashboard at
http://127.0.0.1:8081. Use --admin-port to choose another local port, or
--no-dashboard to start only the public game API. The dashboard refuses to bind
to any address other than 127.0.0.1. It is not served through the public game port.

On first start, a random admin key is saved beside the database in admin-key.
The console prints the file path, not the key. Read that local file and enter
the key into the dashboard. For the default Windows setup:
    Get-Content server/data/admin-key
The key stays in browser memory, not browser storage. Locking or reloading the
page clears access. ADMIN_KEY can supply an existing key of at least 32 ASCII
characters; ADMIN_KEY_FILE or --admin-key-file selects a key-file location.
Restart after changing the key. Keep this key private: it grants operator access.

Dashboard features:
- Search and page through players and levels.
- Grant and revoke moderator access with a recorded reason.
- Issue warnings, or suspend uploads temporarily/permanently; lift suspensions.
- View level content and download it for review.
- Rate levels 1-9 after signing in as a moderator.
- Delete any shared level with a reason and a confirmation.
- Review the latest 50 moderation events.

Upload suspensions apply immediately to existing sessions, new uploads, and
updates of existing levels. They expire automatically when their time passes.
Players can still sign in, play, download, and remove their own levels.
Warnings and suspension reasons appear in the player's account manager.
Actions target account IDs, so changing a username does not evade a suspension.
Deleting a shared level also removes its rating and import provenance; local
downloaded copies are unaffected. Deletion is permanent. Audit history remains.

The admin key permits role management and player/level administration, but a
real moderator session is still required for difficulty ratings. The rating
records that moderator as its author. Public API calls cannot assign moderator
roles or issue punishments. The dashboard validates Host/Origin headers and
requires the admin key on every API request.

Docker on Linux:
    DOMAIN=game.example.com docker compose -f server/compose.yaml --profile admin up -d --build
The optional admin service uses host networking with an enforced loopback-only
listener; no admin port is published. The game-data volume is shared with the
game service. Read the key with:
    docker compose -f server/compose.yaml exec admin cat /data/admin-key
Open http://127.0.0.1:8081 on the server host. For a remote host, use an SSH
tunnel to its localhost port, for example ssh -L 8081:127.0.0.1:8081 user@host.
The Docker admin profile requires host-network support; on Windows, run the
Python server natively for localhost dashboard access. The default Docker game
service runs without a dashboard until the admin profile is enabled.

You can also run only the dashboard against an existing database:
    python server/admin_dashboard.py --database /path/to/game.sqlite3
Do not start this alongside another dashboard on the same port.


### Client version blacklist

Open the local dashboard at `http://127.0.0.1:8081` and use **Client version blacklist**. Enter the numeric compiled build ID (currently `27`, version `2.3.1`) and a reason, then choose Block version or Unblock version. Changes persist in SQLite and appear in moderation history. Blocking applies immediately to account and level requests, including existing sessions, with HTTP 426 and the reason. Local/offline play is unaffected.

Desktop builds embed `version` and `version_id` from `assets/config.json` into `BuildInfo.h` at CMake configuration time. Android's build fixer generates the same native constants and synchronizes Gradle's compiled `BuildConfig` values. Increase `version_id` for every release and rebuild; editing the installed config cannot change the displayed or reported client version. Clients send `DF-New/2.3.1 (build/27)` as their User-Agent.

Use `legacy` to block older official clients that send the old `DF-New/1.0` or `DF-New/1.0-android` identity. Browsers and unidentified/custom clients remain compatible; this tool is version compatibility control, not an anti-cheat or authentication boundary, since modified clients can spoof their identity. Account management in the browser, the private dashboard, health checks, and update manifests/downloads remain available for recovery.
